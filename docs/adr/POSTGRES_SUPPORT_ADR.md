# ADR: PostgreSQL Backend Support

This document records design decisions made when adding PostgreSQL 15+ as a
storage backend alongside the existing SQLite backend.

---

## ADR-001: Per-driver repository packages instead of driver-neutral queries

### Status
Accepted

### Decision
Add a `repository/postgres/` sub-package for each app that is a sibling of
the existing `repository/sqlite/` package. Each sub-package contains SQL
written for its specific driver (PostgreSQL `$N` placeholders, `RETURNING id`,
`BOOLEAN`, `TIMESTAMP`). No attempt is made to share query strings across
drivers via `sqlx.Rebind` or a query-builder abstraction.

### Rationale
- SQLite and PostgreSQL have meaningfully different idioms: `?` vs `$N`
  placeholders, `AUTOINCREMENT` vs `GENERATED BY DEFAULT AS IDENTITY`,
  `INTEGER`/`0`/`1` booleans vs `BOOLEAN`/`TRUE`/`FALSE`, `DATETIME` vs
  `TIMESTAMP`, `LastInsertId()` vs `RETURNING id`.
- A Rebind approach unifies the easy part (placeholders) but leaves all the
  other dialect differences to be handled case-by-case, creating a false
  sense of portability.
- Having two explicit, fully-typed packages makes dialect differences visible
  and auditable. A query change that only applies to one backend is made in
  one file without risk of breaking the other.
- The factory (`repository/factory.go` per app) is the only place that
  branches on `config.Storage.Type`; callers above the factory see only the
  interface.

### Key files
- `internal/authnz/repository/factory.go`
- `internal/listing/repository/factory.go`
- `internal/chat/repository/factory.go`
- `internal/shortener/repository/factory.go`
- `internal/{app}/repository/postgres/` — one package per app

## ADR-002: Single shared `*sqlx.DB` for all apps

### Status
Accepted

### Decision
`cmd/all-in-one/server/server.go` constructs one `*sqlx.DB` via
`internal/storage` and passes it to every app's service constructor
(`NewService(ctx, db, config, log)`). No app opens its own connection.
Repository `Close()` methods are no-ops; the single DB is closed by the
owning server on shutdown.

### Rationale
- Opening one connection per app leads to multiple pools competing for the
  same underlying resource, duplicate OTel instrumentation registrations, and
  independent migration ownership.
- A single pool lets the OS and database server apply resource limits once.
- OTel DB stats metrics (`otelsql.RegisterDBStatsMetrics`) are registered
  once per backend, tagged with `db.system=sqlite` or `db.system=postgresql`.

### Key files
- `internal/storage/storage.go` — factory that returns `*postgresStorage` or
  `*sqliteStorage`
- `internal/storage/postgres.go` — otelsql-wrapped postgres connection
- `internal/storage/sqlite.go` — otelsql-wrapped sqlite connection
- `cmd/all-in-one/server/server.go` — single construction site

## ADR-003: Separate migration directories per backend

### Status
Accepted

### Decision
Schema migrations live in `db/migrations/sqlite3/` and
`db/migrations/postgres/` respectively. Both are versioned identically (01–05
at time of writing) so adding a new migration means adding files to both
directories. `golang-migrate/v4` is used in both cases; the driver is swapped
by the storage implementation.

### Rationale
- Sharing a migration directory would require conditional DDL inside `.sql`
  files, which is non-standard and fragile.
- Identical version numbers make it straightforward to verify parity: every
  SQLite migration has a corresponding Postgres migration and vice-versa.
- The command `go run main.go all-in-one db migrate up` automatically picks
  the correct directory based on `config.Storage.Type`.

### Key schema differences in Postgres migrations
| Table | SQLite | Postgres |
|---|---|---|
| `topics.id`, `items.id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `sessions.access_token_expiry` | `INTEGER` | `BIGINT` |
| `users.totp_enabled` | `INTEGER NOT NULL DEFAULT 0` | `BOOLEAN NOT NULL DEFAULT FALSE` |
| `short_links.is_active` | `BOOLEAN NOT NULL DEFAULT 1` | `BOOLEAN NOT NULL DEFAULT TRUE` |
| `short_links.*_at` | `DATETIME` | `TIMESTAMP` |
| `users`, `topics` order | any (SQLite defers FK checks) | `users` created before `topics`/`sessions` (immediate FK enforcement) |

### Key files
- `db/migrations/sqlite3/` — 5 versions (up + down)
- `db/migrations/postgres/` — 5 versions (up + down)
- `internal/storage/sqlite.go` — `MigrateUp`/`MigrateDown` using `file://db/migrations/sqlite3`
- `internal/storage/postgres.go` — `MigrateUp`/`MigrateDown` using `file://db/migrations/postgres`

## ADR-004: Import-cycle avoidance in chat repository

### Status
Accepted

### Decision
The `internal/chat/repository/postgres/` sub-package exports a plain concrete
`Storage` struct with exported fields and no reference to the parent
`repository` package. The adapter that implements the `repository.Storage`
interface lives in `internal/chat/repository/postgres.go` (package
`repository`), which imports the sub-package.

### Rationale
- The parent `repository` package defines interfaces used by the service
  layer. If the `postgres` sub-package imported those interfaces, a cycle
  would form: `repository` → `postgres` → `repository`.
- Moving the adapter into a file in `package repository` (rather than the
  sub-package) breaks the cycle while keeping all interface-satisfaction code
  in one place.
- This pattern is already established by the `sqlite.go` adapter in the same
  package.

### Key files
- `internal/chat/repository/postgres/storage.go` — exported `Storage` struct,
  no parent import
- `internal/chat/repository/postgres.go` — adapter in `package repository`
- `internal/chat/repository/sqlite.go` — identical pattern for SQLite

## ADR-005: OTel instrumentation via otelsql

### Status
Accepted

### Decision
Both SQLite and PostgreSQL connections are opened via
`github.com/XSAM/otelsql` which wraps `database/sql` to emit traces and
connection-pool metrics automatically. The `db.system` attribute is set to
`"sqlite"` or `"postgresql"` at open time.

### Rationale
- Zero per-query instrumentation code in repositories; traces appear
  automatically.
- DB pool metrics (open connections, wait count, etc.) are emitted as
  standard OTLP metrics with the backend tag for filtering in dashboards.
- See `docs/metrics.md` for the full list of emitted metrics and attribute
  values.

### Key files
- `internal/storage/sqlite.go` — `otelsql.Open("sqlite3", …)`
- `internal/storage/postgres.go` — `otelsql.Open("postgres", …)`

## ADR-006: SQLite FK enforcement moved to central DSN

### Status
Accepted

### Decision
`?_foreign_keys=on` is appended to the SQLite DSN in `internal/storage/sqlite.go`
rather than in the shortener's own repository constructor.

### Rationale
- Before the shared-pool refactor, the shortener opened its own connection and
  added the pragma in its DSN. After unification, only one connection is
  opened, so the pragma must live in that single DSN.
- Enforcing FK constraints centrally protects all apps, not just shortener.

## ADR-007: Local development via docker-compose

### Status
Accepted

### Decision
A `docker-compose.yml` at the repository root provides a `postgres:15` service
configured with the default dev credentials (`allinone/allinone/allinone`).

### Quick start (Postgres backend)
```bash
docker compose up -d postgres
export ALLINONE_STORAGE_TYPE=postgres
export ALLINONE_STORAGE_POSTGRES_USER=allinone
export ALLINONE_STORAGE_POSTGRES_PASSWORD=allinone
export ALLINONE_STORAGE_POSTGRES_DBNAME=allinone
go run main.go all-in-one db migrate up
go run main.go all-in-one server
```

### Key files
- `docker-compose.yml`
- `config/config.yml` — `storage.postgres.*` defaults
- `internal/config/config.go` — `PostgresConfig`, `ALLINONE_STORAGE_POSTGRES_*` env binds

## ADR-008: Bidirectional data migration via `db:transfer` CLI command

### Status
Accepted

### Decision
Add a `db:transfer` subcommand to the existing CLI that copies all application
data between backends in either direction:

```bash
# SQLite → PostgreSQL
go run ./cmd/all-in-one db:transfer --direction sqlite-to-pg

# PostgreSQL → SQLite  (requires --confirm to protect the SQLite file)
go run ./cmd/all-in-one db:transfer --direction pg-to-sqlite --confirm
```

### Rationale
- Switching backends requires moving existing data, not just applying schema
  migrations. A dedicated command makes the migration explicit and auditable.
- The tool is implemented in Go (not a shell script) so it reuses the same
  drivers (`go-sqlite3`, `lib/pq`) and type-handling already in the project,
  avoiding external CLI dependencies.
- All writes happen inside a single transaction on the destination — the
  transfer is atomic; a partial failure rolls back completely.
- Rows are read entirely into memory before the transaction begins, keeping
  the source connection read-only and avoiding long-held read locks on SQLite.
- `--confirm` is required for `pg-to-sqlite` to prevent accidental overwrites
  of the production SQLite file (`all-in-one.db`).

### Type-conversion details
Two columns require explicit conversion between backends:

| Column | SQLite type | PostgreSQL type | Handled by |
|---|---|---|---|
| `users.totp_enabled` | `INTEGER` (0/1) | `BOOLEAN` | `boolInt` custom scanner + `boolForDst()` |
| `short_links.is_active` | `INTEGER` (0/1) | `BOOLEAN` | same |
| all `*_at` timestamps | RFC3339 string or `time.Time` | `time.Time` | `nullableTime` custom scanner |

### Insertion order (respects FK dependencies)
`users` → `sessions` → `topics` → `items` → `chat_sessions` →
`chat_session_participants` → `chat_messages` → `chat_invites` →
`recovery_codes` → `totp_challenges` → `short_links` → `short_link_owners`

### PostgreSQL sequence reset
After a `sqlite-to-pg` transfer, `topics.id` and `items.id` (IDENTITY columns)
are inserted with their original SQLite values. The tool calls
`setval(pg_get_serial_sequence(...))` inside the same transaction so future
inserts don't collide with the transferred IDs.

### Key files
- `cmd/all-in-one/db/transfer.go` — transfer logic and custom scanner types
- `cmd/all-in-one/command/command.go` — `db:transfer` command registration
